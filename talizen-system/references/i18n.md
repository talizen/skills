# Talizen Internationalization

Talizen multilingual content is field-level: one CMS item holds every language,
translations live under `_i18n`, and `talizen/cms` decodes fields to the current
locale on read. Do not create one item per language or translation-group keys.

## Enable

Add `i18n` to `talizen.config.ts`, or use editor Settings / Languages.

```ts
export default {
  i18n: {
    defaultLocale: "en",
    locales: ["en", "zh", "ja"],
    localeDetection: true,
  },
}
```

## Routing

- Default locale has no prefix: `/about`.
- Other locales are prefixed: `/zh/about`, `/ja/about`.
- The platform first checks locale-specific pages such as `/pages/zh/About.tsx`
  or `/pages/[lang]/About.tsx`, then falls back to shared `/pages/About.tsx`.
- Prefer shared pages plus locale-aware data; use per-locale files only when
  layout genuinely differs.
- Avoid `[lang]/Index.tsx` as a root catch-all with default-no-prefix routing
  because it greedily matches top-level paths.

## Domain Routing

Locale-specific domains are supported through `i18n.domains` in
`talizen.config.ts`.

```ts
export default {
  i18n: {
    defaultLocale: "en",
    locales: ["en", "fr"],
    domains: [
      { domain: "example.com", defaultLocale: "en" },
      { domain: "example.fr", defaultLocale: "fr" },
    ],
  },
}
```

`example.fr/about` serves French without `/fr`. Locale detection or explicit
locale prefixes can redirect to the configured domain for that locale. Domains
listed here must also be bound to the same site in Settings → Domains.

## Links And Language Switching

Use Talizen's locale-aware `<Link>` for multilingual internal links. It
auto-prefixes the current locale. Never use router libraries.

```tsx
import { Link, useLocale } from "talizen"

<Link href="/blog/hello">Read</Link>

function LangSwitcher() {
  const { locales } = useLocale()
  return (
    <nav>
      {locales.map((locale) => (
        <Link key={locale} href="/" locale={locale}>{locale}</Link>
      ))}
    </nav>
  )
}
```

For raw URL strings, use `localizedPath("/blog", locale?)`. A plain
`<a href="/blog">` does not add locale prefixes.

The `CREGHT_LOCALE` cookie represents an explicit user choice. Detection order
for unprefixed paths is: `CREGHT_LOCALE` cookie, `Accept-Language`, then default
locale. Set the cookie only on deliberate language choice.

## Reading Locale

Use the accessor for the execution context:

- Server-side data functions: `getLocale()` from `talizen` (v0.2.3+) or
  `context.locale` when context is already available.
- Components: `useLocale()` from `talizen`.

Do not parse request URLs or query params to detect locale; the router strips
the locale prefix.

```tsx
import { getLocale } from "talizen"
import { listContents } from "talizen/cms"

export async function getServerSideProps(context) {
  const { locale } = getLocale()
  const { list } = await listContents("blogs", { limit: 10 })
  return { props: { locale, list } }
}
```

CMS values are already decoded to the current locale. Usually branch only for
locale-specific static UI copy or layout.

## UI Text

For strings written in code, use `/messages/{locale}.json` with
`useTranslations()` in components or `getTranslations()` in server-side data
functions.

```json
{ "home": { "title": "Welcome" } }
```

```tsx
import { useTranslations } from "talizen"

function Hero() {
  const t = useTranslations("home")
  return <h1>{t("title")}</h1>
}
```

Keep the default locale file complete; missing keys fall back to it. Use
`/messages` for UI text and `_i18n` for CMS content.

## CMS Storage

Base fields are the default locale. Translations for other locales live under
`_i18n[locale]`, only for fields marked localizable.

```json
{
  "title": "Hello",
  "slug": "hello",
  "cover": "https://cdn.example.com/a.png",
  "_i18n": {
    "zh": { "title": "你好", "slug": "ni-hao" },
    "ja": { "title": "こんにちは", "slug": "konnichiwa" }
  }
}
```

On read, `_i18n[currentLocale]` overlays base fields. Content without `_i18n`
needs no migration.

## Localizable Fields

Usually localizable:

- title, subtitle, summary, body, rich text
- slug and SEO text
- image alt text, captions, button labels

Usually not localizable:

- ids, booleans, numbers, dates
- enum/select values used in logic
- relation/reference fields
- media URLs unless each locale truly needs different media

For enum labels, keep enum values stable and translate display labels with
schema `enumLabelsI18n`.

## Slugs And Relations

Slugs are localized output, not stable identity. Anchor joins and relations on
stable item ids, not per-locale slugs. A relation points to one item that
resolves fields for the current locale.

## Translation Workflow

When making a site or collection multilingual:

1. Add `i18n` config.
2. Mark only text-like CMS fields as `localizable`.
3. Keep shared pages unless layout differs.
4. Write translations under `_i18n[locale]`, leaving ids, enums, booleans,
   numbers, relations, and media keys stable.
5. Use `/messages` for static UI copy.
6. Verify links use `<Link>` or `localizedPath()`.

## Do / Don't

- Do put translations under `_i18n[locale]`.
- Do read locale with `getLocale()`, `context.locale`, or `useLocale()`.
- Do let `talizen/cms` decode localized fields.
- Don't duplicate whole CMS items per locale.
- Don't manually parse URLs for locale.
- Don't use plain anchors for multilingual internal navigation when locale must
  be preserved.
